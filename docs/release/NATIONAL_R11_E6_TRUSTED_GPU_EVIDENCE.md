## 2. Why a guest cannot self-certify release

The existing E5 browser verifier in `scripts/national-qa/gpu-attestation.mjs` verifies a version-1 Ed25519 detached signature over `JSON.stringify(proof.payload)`, binds the exact source SHA, GitHub run/attempt, runner name, nonce and short-lived host/guest GPU facts. Its reviewed fingerprint enrollment file `scripts/national-qa/trusted-gpu-keys.json` currently has **zero enrolled keys**. This intentionally blocks trusted release. No signing key is installed or generated by E6.

Before this change, the E6 sanitizer could set `hardware.proofAccepted=true` based on an event in **guest-written** `acceptance.json`. It still set final `releaseCertified=false`, but a mode-level `outcome=PASS` could be misread as an independent release PASS. **R11 fixes that ambiguity:** the sanitizer now treats an E5 browser-reported signature result as `hardware.browserClaimedSignedProof` (an untrusted claim), sets `hardware.proofAccepted=false`, and never emits a release-mode accepted verdict on the guest. Diagnostic success is unaffected; missing screenshots fail closed. The new screenshot SHA-256 manifest binds every allowlisted image to each redacted mode report; raw packets, console, worker state, private logs and host secret material remain excluded.

A post-job verification process **outside the disposable GPU guest** is now implemented as `scripts/national-gpu-ci/verify-independent-release.mjs`. This is deliberately **not** called inside the GPU workflow: the guest must have been destroyed before the postflight can be observed. The verifier does not import any public key or root from an artifact, E5 browser report or signed proof.

## 3. Required controller/operator witness contract (not yet supplied)

A trusted external host controller/operator must independently observe and sign both records. Both signatures use **Ed25519** over UTF-8 `JSON.stringify(payload)`; private keys remain exclusively outside the KVM guest. The reviewed E5 enrollment SHA-256 fingerprint and a separate host-owned trust policy must **both** authorize the supplied host-side SPKI PEM key. No auto-enrollment or `proof.publicKey` fallback exists.

**Trusted run context** must be obtained independently from GitHub Actions' control plane (not `summary.json`): repository `LeviCade/OpenFront-National`, immutable repository ID `1459234894`, exact 40-character candidate SHA, numeric run ID/attempt, concrete `skybot-ci-gpu-*` runner name and numeric runner ID, randomly generated **64-hex run challenge**, and independently observed job start/completion milliseconds. The expected runner must be the actual assigned physical Skybot guest, not merely the requested label. Validate current writer/owner authorization and reviewed staging ancestry upstream before any GPU acquisition.

**Preflight proof** uses E5's signed `payload.version=1` contract, extended with `repository`, `repositoryId`, and `runnerId` (E5 may safely ignore the extra signed fields). It contains source, run, attempt, runner, challenge, bounded `issuedAtMs`/`expiresAtMs` (maximum 120 seconds), host physical GPU and lease facts, and signed guest VirGL backend/WebGL1/WebGL2 renderer and shader pixels. Required host chain: vendor `8086`, device `0412`, driver `i915`, render `/dev/dri/renderD128`, KVM and verified VirGL transport. **E5's short TTL may require trusted refreshed per-mode preflights during four serial browser tests**; the current controller has not demonstrated that broker contract. E6 does not weaken E5's TTL.

**Postflight proof** is a *second detached signature*, captured after GitHub's job completion on the physical host/controller. Required payload:

```json
{
  "version": 1,
  "purpose": "skybot-gpu-postflight-v1",
  "repository": "LeviCade/OpenFront-National",
  "repositoryId": "1459234894",
  "sourceSha": "<exact 40 lowercase hex>",
  "runId": "<numeric string>",
  "runAttempt": "<numeric string>",
  "runnerName": "skybot-ci-gpu-<actual runner suffix>",
  "runnerId": "<GitHub-assigned numeric string>",
  "challenge": "<random 64 lowercase hex>",
  "observedAtMs": 1780000000100,
  "evidenceSha256": "<SHA-256 of exact byte-for-byte redacted summary.json>",
  "host": {
    "deviceVendorId": "8086",
    "deviceId": "0412",
    "driver": "i915",
    "renderNode": "/dev/dri/renderD128"
  },
  "cleanup": {
    "vmDestroyed": true,
    "gpuLeaseReleased": true,
    "renderNodeAclRestored": true,
    "overlayDestroyed": true,
    "tmpfsResidueCleared": true,
    "efiResidueCleared": true,
    "browserProcessesTerminated": true,
    "privateLogsDestroyed": true,
    "ephemeralRunnerDeregistered": true,
    "cpuCapacityUnaffected": true
  }
}
```

This is **schema documentation, not an actual signed receipt**. The real proof is `{ "payload": { ... }, "signature": "<64-byte Ed25519 signature, base64>" }`; every field, including cleanup, is signed. All ten cleanup facts must be directly observed on the host and true; an absent flag fails. The postflight time must be after job completion and no later than one hour afterward. The host's preflight and postflight GPU identities must agree. A source/run/runner/nonce swap, changed summary, altered or symlinked screenshots, wrong viewport, failed gameplay, absent key enrollment or guest-hosted proof fails closed.

**Production execution boundary:** on an independently controlled host **after the ephemeral guest is gone**, place the independently acquired, access-controlled files in `/etc/skybot-ci/national-gpu-release/` as named by the CLI. The verifier reads the reviewed E5 fingerprint enrollment from the exact checked-out source and requires that fingerprint also be present in host-owned `host-trust-policy.json`. The optional host command `node scripts/national-gpu-ci/verify-independent-release.mjs` emits only a sanitized signed-verdict *verification result* (not a new private signature). It refuses execution under `GITHUB_ACTIONS=true`; no guest-provided trust path argument exists. Production source checkout must itself be verified against the approved immutable commit by the host.

**Scope of generated code:** verifier and synthetic tests are ready. The Skybot controller's actual out-of-guest preflight signer, key enrollment and per-run postflight signer/observer, secure evidence handoff, live teardown observation and verified GitHub runner ID are **external dependencies**. No physical host audit has been executed here. A positive synthetic signature test does **not** establish a real host signing service.

## 4. Evidence privacy and artifact storage audit

At this checkpoint `LeviCade/OpenFront-National` is a **PUBLIC** GitHub repository, not one of the owner's private repositories. The central policy in `LeviCade/GH-Artifacts/docs/PRIVATE_ARTIFACT_STORAGE_POLICY.md` and `OWNER-WIDE-ONBOARDING.md` explicitly says **public repos use GitHub-native artifacts; do not grant them private Drive federation**. The private Workload Identity Federation provider excludes public repositories. Therefore the existing `actions/upload-artifact@v4` for this public repo is the correct supported provider **today**, not a policy violation. Converting to Drive using owner-private credentials would broaden access dangerously.

The present diagnostic uploads only `national-qa-artifacts/gpu/public/diagnostic/`, with 7-day native artifact retention; the strict workflow uploads only `.../public/release/`, with 14-day retention. No raw browser logs, packet payloads, host inventory, signer PEM or controller/lease files should enter either archive. The current `release` area now contains **guest-only, non-certified** records until an independent postflight verdict is issued separately. Images are limited to approved stage names, 30 per mode, 4 MiB each, bounded PNG structure, no symlink. Screenshot digest manifests are redacted hashes, not image bytes. **Public-repo artifacts and screenshots may be accessible to repository viewers**; do not put private person/host information in images. A private/restricted release vault requires a separately reviewed secure broker or repository visibility change and new IAM review, not silent WIF reuse.

No extra GPU jobs, experimental GPU matrix, repeated installs, or CI replays were introduced. The working diagnostic still uses **one owner-authorized reviewed SHA, one `skybot-ci-gpu` allocation, one pinned dependency install, four serial real E5 browser invocations, one bounded collector upload**. Focused crypto/collector tests run locally; no new CI job is added.
